What the prompt asks the model to do

Disambiguate hierarchical intents, ignore menu noise, honor corrections, extract distinct secondary topics, preserve supported facts, suppress synthetic identifier canaries, and apply archived-confidence rules.

Thirteen cases cover thirteen scenario families, not every route. The strict exact-match rubric is not a general model-quality score; newly generated free-form explanations are not independently evaluated for meaning.

This is not the Azure Batch API.

Each of five client-side groups sends its records one at a time; the groups run concurrently against the same online deployment. At 1,700 records, that is exactly 5 × 340.

The checked public US catalogs did not list GPT-5 mini DataZoneBatch. A retail pricing meter does not prove a deployment SKU is available. Model/SKU availability must be rechecked in your subscription.

A controlled reproduction of a pattern.

The 150K allocation, three-attempt policy, 90-second request timeout, and 2,048-token output ceiling are explicit test assumptions—not a claim to reproduce an unknown production environment exactly.

Bounded initial unpaced traffic, service-guided retries, durable local checkpoints, and a 10-hour admission deadline per mode. Conservative all-attempt model estimate: @@V3_BUDGET@@, not an invoice.

When you see 429s

  1. Measure demand and limits.

    Capture actual prompt/output/reasoning usage and returned rate-limit headers. A tokenizer estimate is not the service's complete accounting.

  2. Coordinate admission and retries.

    Use shared pacing, respect retry guidance, avoid stacked retry layers, and retain every failed attempt.

  3. Match capacity to the deadline.

    Review approved quota and cost before increasing allocation. Use service Batch only when its separate quota and asynchronous turnaround fit.

  4. Re-evaluate answer quality.

    Prompt reduction and model changes can alter accuracy. Keep schema checks, semantic checks, and throughput separate.

Existing Microsoft framework

Durable work, not a custom workflow engine.

The Azure path uses Durable Functions and Durable Task Scheduler: authenticated kickoff, activities, durable timers, and a shared Batch admission coordinator.

Private Blob artifacts and Table metadata support reconciliation; local runs use SQLite. Managed identity and Entra authentication keep keys out of code.

The v3 grouped reproduction runs on the client host, not inside the Batch service. Neither local locks nor the cloud coordinator govern unrelated traffic outside their scope.

Read this before drawing conclusions

What these results do—and do not—show.

  • These are synthetic reference experiments, not production benchmarks, a performance SLA, or a zero-429 guarantee.
  • Compare matched inputs within a test. Different record counts, models, allocations, output budgets, cache states, and prompts are not directly interchangeable.
  • Full wall time includes waiting and failures. Do not infer per-record Batch latency by dividing total turnaround by record count.
  • Schema-valid output is not semantic accuracy. Exact-match synthetic grading has its own limitations and does not replace evaluation on an authorized real workload.
  • Usage estimates apply configured token rates to reported usage. They are not invoices and exclude infrastructure, missing usage, taxes, and billing adjustments.
  • US Data Zone inference is broader than a single resource region. Verify current model/SKU availability, quota, network access, and residency requirements before deployment.
  • This static page is built from committed public evidence. V3 progress is timestamped; it does not refresh directly from the running job or any Azure endpoint.
  • Keep real customer records, credentials, private configuration, and raw cloud logs out of public repositories and demos.
